# Benchmark 内页内容标准

本文档定义 Lens Frontier 单个 Benchmark 内页的内容契约。页面的视觉、图表和交互可以由各项目继续完善，但公开信息必须使用一致的语义、版本和证据口径。

适用路由：`/<lang>/bench/<benchmark-id>/`

## 原则

1. **先给结果，再解释结果**：读者首先看到 Leaderboard 和当前版本，再逐层查看 Task、Method、Evidence、Analysis 与限制。
2. **一个事实只维护一次**：Data Card 是结构化事实的唯一来源；Blog 用于论文、方法、发布说明和分析，不重复抄写整张 Data Card。
3. **开发自由，数据契约统一**：可以选择适合项目的图表和交互，但不得更改字段含义、隐藏缺失状态或把 mock 值当成正式结果。
4. **事实、推断和待验证内容分开**：分析结论必须能回到版本化结果或 evidence；未完成内容明确标记为待补充。
5. **先保护公开边界**：凭证、个人数据、受限材料和未获授权的样本不得进入页面或 PR 描述。

## 建议的信息顺序

### 1. Overview / Identity（必需）

页面首屏应让读者在很少的信息内理解项目：

- 正式名称和稳定 `id`。
- 一句话能力主张，以及约 200 字简介。
- 可公开署名的作者或维护方、当前状态和最近更新时间。
- Benchmark 版本、协议版本、主指标和分数方向。
- 数据来源、judge / verifier 模式、公开范围和可用链接。
- 明确写出“测什么”和“不支持推出什么”。

首屏不应放没有解释价值的装饰指标，也不应使用未公开候选名称或开发期 mock 分数填满页面。

### 2. Leaderboard（有公开结果时必需）

Leaderboard 负责回答同一 Benchmark 下不同模型的表现，不负责承载完整方法说明。

每项结果至少包含：

- 精确模型和版本标识。
- 标准化分数、原始指标与单位。
- Benchmark 版本、协议版本和评测日期。
- 运行次数；具备条件时提供不确定性或置信区间。
- `verified`、`reviewed` 或 `pending` 的 evidence 状态。
- 可公开记录、报告、artifact 或哈希索引。

图表是默认主视图。模型很多时，可以通过筛选、滚动、分页或局部放大管理密度；不可通过省略标签让读者无法判断模型身份。表格只在需要精确检索、复制或下载时作为补充。

没有通过审核的真实结果时，显示当前阶段和缺失原因，不渲染占位排名。

### 3. Tasks（Data Card 必需）

Task 区域需要让读者看到模型实际面对什么，而不只是能力标签：

- 任务总量、任务族和每个任务族的数量或占比。
- 至少一个可公开 Task specimen。
- 输入、上下文、可用工具或环境，以及完成判定 assertions。
- 任务来源、筛选和改造方式。
- 只展示许可允许公开的原始实例或等价脱敏实例，并说明脱敏对任务含义的影响。

推荐展示 1-3 个代表实例；完整数据集应通过仓库、文档或下载入口提供，而不是把所有样本塞进页面。

### 4. Method（Data Card 必需）

Method 区域至少说明：

- 数据来源、采样、split、去重和污染控制。
- 执行环境、工具、时间、网络、预算、重试和模型参数限制。
- 主指标、原始指标、聚合方式和缺失值处理。
- verifier、judge 模型、提示或专家 rubric 的版本。
- 人工复核覆盖率、分歧裁决和异常重跑规则。

方法变更会影响可比性时，必须升级协议版本并在版本记录中说明。

### 5. Evidence（正式发布必需）

Evidence 区域负责回答“为什么相信这个分数”：

- 保留的输出、日志、trace、截图、测试和 judge records。
- evidence 深度是 `full` 还是 `partial`。
- 自动验证、人工 review 和专家审计各自覆盖多少结果。
- 记录包、稳定链接、对象存储位置或哈希索引。
- 复现所需的环境、依赖和访问条件。

Evidence 状态描述审核深度，不等同于“分数已经出现在代码里”。

### 6. Analysis / Findings（有数据时建议）

分析应该帮助读者理解能力区分，而不只是重复排名：

- 分数分布、模型间差距和是否出现饱和。
- 各任务族得分和模型能力剖面。
- 失败模式、样本量和占比。
- 代表性成功/失败案例。
- 2-5 条由当前数据支持的主要发现。
- 结论的适用范围，以及仍需验证的问题。

图表需要对应明确问题。没有趋势含义的数据不使用折线，不能支持中位数解释时不展示中位数。

### 7. Limitations / Versions / Access（必需）

页面末段至少保留：

- 偏差、泄漏、主观性、饱和、领域覆盖和不适用场景。
- Benchmark、协议、rubric 和模型版本历史。
- 版本变更是否仍可横向比较。
- license、引用方式、仓库/文档/数据下载和联系入口。
- 公开资源的稳定链接；不可公开的资源只说明缺失会造成什么复现限制。

## Blog 与文章分析页

原有论文、Benchmark 方法文章和评测分析继续保留在 `src/content/`，并保持原 slug、作者、日期、标签、图片和阅读量 ID。它们是正式研究输出，不应为了建设 Bench 内页被删除或搬成重复的 Data Card。

适合单独发布 Blog 的内容包括：

- 正式论文或预印本。
- Benchmark 发布背景和方法创新。
- 重要版本更新及其可比性影响。
- 模型结果分析、失败模式研究和评测争议。

只有分数修正、字段补齐、链接替换或状态更新时，修改 Data Card 和版本记录即可。

## 代码映射

维护者将审核后的资料映射到以下文件：

```text
src/lib/benchmarkData.ts        # Identity、目录状态和 Data Card 摘要
src/lib/benchmarkResults.ts     # 审核后可公开的真实榜单结果
src/lib/benchmarkDetailData.ts  # Tasks、Method、Evidence、Analysis 和 Versions
src/content/                    # 独立论文、方法文章和分析，不作为 Data Card 数据源
```

榜单结果可以使用 `templates/benchmark-results.csv` 或等价的机器可读文件提交。大型公开数据和运行日志不直接复制进站点仓库，应提供稳定、许可清楚的公开引用。

## 发布门槛

### Data Card 预览

- [ ] Identity 和简介能够由公开资料核对。
- [ ] 至少一个 Task specimen 可公开。
- [ ] Method、评分协议和限制不是通用占位内容。
- [ ] 缺失内容明确标记状态，不用 mock 填充。

### 公开 Leaderboard

- [ ] 所有数字来自真实运行和可计算结果文件。
- [ ] 模型、Benchmark、协议和 rubric 版本能够对应。
- [ ] 分数方向、聚合方式、运行次数和 evidence 状态已说明。
- [ ] 结果顺序与提交的 CSV 一致。

### 正式发布

- [ ] Evidence、版本记录和限制足以复核主要结论。
- [ ] Findings 能回到具体数据，不把推断写成事实。
- [ ] 任务实例、链接、署名和公开范围已经完成发布审核。
- [ ] `pnpm check` 通过，并检查中英文详情路由和移动端布局。
